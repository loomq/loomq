## 2. 失败测试（先红）

### 2.1 `BugUpdatePostCommitFailureTest`

- 场景：`UpdateThrowingStore.update()` 抛错，模拟 `persistStateChangePutOnly` 成功入 mmap 后、内存镜像更新失败。
- 期望：`updateIntent` 不抛错，返回新 `executeAt`；重启后仍读到新调度。
- 修复前：`updateIntent` 直接抛出 `IllegalStateException`。

### 2.2 `BugTriggerScanRejectedExecutionTest`

- 场景：把已 `shutdown` 的 `ScheduledExecutorService` 放入 `scanSchedulers`，再调用 `triggerScan`。
- 期望：`pendingScanTrigger` 复位为 `false`。
- 修复前：`submit` 抛 `RejectedExecutionException`，标志保持 `true`。

### 2.3 `BugUpdateIntentValidationTest`

- 场景：
  - updater 把 `deadline` 改成早于 `executeAt`；
  - updater 设置 `RedeliveryPolicy(maxAttempts=0)`。
- 期望：均抛出 `IllegalArgumentException`。
- 修复前：均静默成功。

### 2.4 `BugSchedulerFinalizeStoreUpdateFailureTest`

- 场景：`UpdateThrowingStore.update()` 抛错，投递返回 `SUCCESS`，注册 observer 统计 `onDelivered`。
- 期望：即使内存镜像更新失败，`onDelivered` 仍触发。
- 修复前：异常被 `runFinalizeTask` 吞掉，`onDelivered` 计数为 0。

## 3. 修复设计

### 3.1 `updateIntent` 提交后保护

**文件**：`loomq-core/src/main/java/com/loomq/application/command/IntentCommandService.java`

**问题**：

`updateIntent` 的提交点与 `cancelIntent` / `fireNow` 不一致：

```java
persistStateChangePutOnly(intent); // 已写入 mmap + locationIndex
persisted = true;
intentStore.update(intent);        // 这里失败会进入 catch
...
awaitDurableCommit();              // 这里失败也会进入 catch
```

旧 catch 无条件回滚 `executeAt/status/revision`，但磁盘/索引已经是新值。

**修复**：

在 `catch` 开头增加 `if (persisted)` 分支：

- 不回滚内存调度状态；
- 若 `reschedule == true`，按新状态补做 `scheduler.restore/schedule`（与正常成功路径同一收口）；
- 返回 `Optional.of(intent.copy())`，与 cancel/fireNow 的“提交后失败即成功”语义对齐；
- 记录 `logger.warn("Update committed; ignoring post-commit failure...")`。

只有 `persisted == false`（updater 抛错、校验失败、持久化写失败）才走原有回滚路径。

### 3.2 `updateIntent` 更新后校验

**位置**：同上，在 `newExecuteAt` 应用后、`incrementRevision()` 前调用：

```java
IntentValidator.validate(intent);
```

这样 updater / `newExecuteAt` 引入的非法 `deadline`、`redelivery`、`expiredAction` 等会在持久化前被拒绝，且因为 `persisted == false` 会走原有回滚重排逻辑。

### 3.3 `triggerScan` 关闭竞态容错

**文件**：`loomq-core/src/main/java/com/loomq/application/scheduler/PrecisionScheduler.java`

**问题**：

`stop()` 先 `shutdown()` 后 `clear()`，窗口内 `scanSchedulers.get(tier)` 非 null 但 executor 已终止，`submit` 抛 `RejectedExecutionException`，`pending` 标志无人复位。

**修复**：

```java
try {
    scanScheduler.submit(() -> { pending.set(false); scanAndDispatch(tier); });
} catch (RejectedExecutionException e) {
    pending.set(false);
    logger.warn("triggerScan rejected for tier {} during shutdown; resetting pending", tier);
}
```

### 3.4 调度器 `IntentStore.update` best-effort

**文件**：`loomq-core/src/main/java/com/loomq/application/scheduler/PrecisionScheduler.java`

**问题**：

`finalizeIntent` / `handleDeliveryFailure` / `settleTerminal` / `scheduleRetryOrHonorReschedule` 中，`intentStore.update` 失败会中断后续 `persistTerminal`、observer 通知或重排程。

**修复**：

新增私有方法：

```java
private void updateStoreBestEffort(Intent intent) {
    try {
        intentStore.update(intent);
    } catch (Exception e) {
        persistFailures.incrementAndGet();
        logger.error("intentStore.update failed for intent {}: {}", intent.getIntentId(), e.getMessage(), e);
    }
}
```

将调度器内全部 6 处 `intentStore.update(intent)` 替换为 `updateStoreBestEffort(intent)`。

理由：`IntentStore` 只是热态内存镜像，不是持久化权威；其更新失败不应阻塞投递结果结算。

## 6. 风险与后续

- `updateIntent` 提交后 `store.update` 失败时，`ConcurrentIntentStore` 的 `statusCounts` 等簿记可能不精确；这是与 `cancelIntent` / `fireNow` 相同的既有取舍，磁盘为权威。
- `IntentStore.update` 失败在调度器路径被降级为日志 + `persistFailures` 计数；如果未来需要强一致内存镜像，应引入可重试的内存写或事务边界。
- `triggerScan` 的 `pendingScanTrigger` 在 `start()` 时未统一清空；本次只封住了 `RejectedExecutionException` 路径，后续可在 `start()` 中增加防御性清空。

## 7. 自 review 记录

对 spec 的自我复核结论：

1. **准确性**
   - 4 个问题、5 个失败用例、6 处 `intentStore.update` 替换均与实际代码一致。
   - `updateIntent` 的 `persisted` 提交点描述正确：`persistStateChangePutOnly` 成功后即为“已提交”。

2. **已补充的精度**
   - 3.1 明确“仅当 `reschedule == true` 时才补做调度”，避免读者误解为所有提交后失败都会重新调度。
   - 5 明确未跑 `full-tests`，避免验证范围被高估。

3. **已知覆盖缺口**
   - `updateIntent` 的 `awaitDurableCommit()` 失败路径没有独立测试；当前与 `store.update` 失败共用同一 `persisted` guard，风险较低，但可后续补一条注入 `awaitCommit` 失败的用例。
   - `BugSchedulerFinalizeStoreUpdateFailureTest` 只覆盖 `SUCCESS` 分支；`DEAD_LETTER` / `EXPIRED` / `RETRY` 分支的 `updateStoreBestEffort` 路径未单独测试。
   - `BugTriggerScanRejectedExecutionTest` 使用反射注入已 shutdown executor，属于白盒测试；若调度器字段重构，该测试需要同步更新。

4. **实现与 spec 的小偏差**
   - `updateStoreBestEffort` 复用了 `persistFailures` 计数器，语义上该计数器原本面向持久化失败；内存镜像更新失败也计入其中可能造成指标解读混淆。当前为最小改动，后续可拆独立计数器。
   - `triggerScan` 的 `pendingScanTrigger` 未在 `start()` 统一清空；本次只封住 `RejectedExecutionException` 路径，后续可加防御性清空。
